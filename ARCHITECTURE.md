# Arquitetura

## Padrão: MVVM + feature-based

Cada feature em `src/features/<nome>/` separa três camadas:

- **Model** (`model/`) — tipos de domínio e schemas Zod. Não importa React.
- **ViewModel** (`viewmodel/`) — hooks que orquestram TanStack Query, mutations, Zustand e Socket.IO. Recebem/retornam dados simples, nunca JSX, e não conhecem a rota que os invoca (o roteamento é injetado via parâmetros, ex. `search`/`onSearchChange` em `useCatalogViewModel`).
- **View** (`ui/`) — componentes de apresentação puros, recebendo o retorno do ViewModel como props.

A camada de rota (`src/routes/`) é o ponto de encontro: um arquivo de rota fino lê/escreve o estado da URL, invoca o ViewModel e renderiza a View correspondente — nunca contém lógica de negócio.

`src/shared/` reúne o que é usado por mais de uma feature: hooks (`shared/hooks`), infraestrutura (`shared/lib`: Axios, cliente Socket.IO, QueryClient, aritmética decimal), stores globais (`shared/stores`: sessão) e componentes de UI reaproveitáveis (`shared/ui`: estados vazio/erro, skeleton com shimmer, paginação).

`src/components/ui/` é gerenciado pelo CLI do shadcn/ui (primitivas: Button, Input, Select, Card...) e não deve ser editado manualmente além do necessário para adequar ao design.

## Stack e por que

- **TanStack Router + Vite (SPA)**, não TanStack Start: o desafio pede TanStack Router especificamente; SSR/server functions adicionariam complexidade sem necessidade (MSW é client-side, o deploy é estático).
- **shadcn/ui, preset Nova (base Radix)**: preset padrão do CLI atual, ícones Lucide, fonte Geist Variable.
- **`cn` (pacote oficial shadcn-ui/cn)** substitui `clsx` + `tailwind-merge` diretamente — já é o que os componentes gerados usam.
- **Zustand**: sessão (`shared/stores/session-store.ts`, persistida) e estado de UI do modal de auth (`features/auth/stores/auth-modal-store.ts`, efêmero). O carrinho **não** tem store própria — ele é 100% servidor (mock), lido/escrito via TanStack Query (`['cart']`) como qualquer outro recurso remoto; só a UI efêmera (texto do campo de cupom) mora em `useState` local.
- **`@mswjs/data`** para o "banco" mockado em memória (`src/mocks/db.ts`), com `localStorage` para persistir entre refreshes e uma função de reset determinístico (`resetScenario`).
- **`decimal.js`** (`shared/lib/money.ts`) para toda aritmética em ETH — valores trafegam como string decimal ponta a ponta (API mock → cache → UI) para não perder precisão.
- **Erros tipados**: `shared/lib/http.ts` normaliza qualquer erro do Axios em uma classe `ApiError` (com `kind`: `validation` | `unauthorized` | `forbidden` | `not_found` | `conflict` | `transient` | `unknown`), registrada como o tipo de erro padrão do TanStack Query via `declare module '@tanstack/react-query' { interface Register { defaultError: ApiError } }`.

## Política de cache (TanStack Query)

Definida em `src/shared/lib/query-client.ts`:

- Queries: `staleTime` de 30s, sem refetch automático ao focar a janela — atualizações de preço/disponibilidade chegam via Socket.IO e escrevem direto no cache (`queryClient.setQueriesData`), então polling entraria em conflito com esses patches.
- Retry automático apenas para status transitório (5xx ou falha de rede), no máximo 2 tentativas; erros 4xx nunca são re-tentados automaticamente.
- Mutations nunca são re-tentadas automaticamente — o fluxo de pedido usa idempotência explícita (`shared/hooks/use-idempotency-key.ts`), não retry silencioso, para nunca duplicar uma compra.
- Chave de query do catálogo inclui todos os parâmetros de busca (`['catalog', 'list', search]`): cada combinação de filtros é uma entrada de cache independente, então uma resposta atrasada de uma busca antiga nunca sobrescreve o resultado da busca atual — resolve "respostas fora de ordem" sem lógica adicional.

## Atualização otimista

`useToggleFavorite` (`src/features/favorites/viewmodel/use-toggle-favorite.ts`) aplica o toggle imediatamente em todas as páginas de catálogo em cache **e** no cache de `['nft-detail', id]` se estiver carregado (`onMutate`), guarda os snapshots anteriores e faz rollback exato em `onError`. Ao final (`onSettled`), invalida ambos para reconciliar com o servidor. É a mesma mutation usada pelo catálogo, pelo detalhe e pelos cards de "Mais desta coleção" — um único lugar de verdade para favoritar.

- **Falha visível, não só revertida em silêncio**: `onError` também mostra um toast com a mensagem do erro — antes o rollback acontecia sem nenhum aviso (gap conhecido, inclusive para o próprio 401 de favoritar deslogado). Cenário de mock dedicado `'forbidden'` faz `POST /api/favorites` responder 403 (`ApiError.kind: 'forbidden'`, existia no tipo desde o início mas nunca tinha sido exercitado por nenhum endpoint) — é o único 403 real do mock hoje, usado especificamente para testar esse caminho de falha+rollback+toast em `e2e/nft-detail.spec.ts`.

## Tempo real (Socket.IO)

- `shared/lib/socket.ts`: singleton preguiçoso; `resetSocket()` derruba a conexão e remove todos os listeners — chamado no logout (`features/auth/viewmodel/use-logout.ts`) para nunca deixar uma subscription da sessão anterior viva.
- `shared/lib/realtime-event.ts`: `createEventVersionTracker()` guarda a maior versão vista por id de recurso e descarta eventos com versão igual ou menor — tolera duplicatas e eventos antigos sem regredir estado mais novo (`nft.updated` carrega `id`, `resource`, `version`).
- Tanto `useCatalogViewModel` quanto `useCartViewModel` assinam `nft.updated` e fazem `queryClient.setQueryData` direto no cache correspondente (`['catalog']` / `['cart']`); no carrinho, além de recalcular preço/desconto/total, uma alteração relevante (preço mudou, ou o item ficou esgotado) também dispara um toast — cobre literalmente o cenário da seção 7 do enunciado ("um NFT está no carrinho, seu preço/disponibilidade muda, a interface informa e atualiza o resumo").
- **Reconciliação pós-reconexão** (`shared/hooks/use-socket-reconnect-reconciliation.ts`, montado uma única vez em `src/routes/__root.tsx`): assina `connect` no socket e distingue a primeira conexão de uma reconexão de verdade via uma flag local (`hasConnectedBefore`) — o evento `connect` dispara nas duas situações, então sem essa distinção toda montagem da árvore geraria um refetch redundante. Numa reconexão real, invalida `['catalog']`, `['cart']`, `['order']` e `['nft-detail']` de uma vez — cobre qualquer alteração perdida enquanto o socket estava caído, inclusive para queries que não têm handler de evento próprio (ex.: o detalhe do NFT só reflete `nft.updated` ao vivo através dessa reconciliação, não de uma assinatura direta). Testado em `e2e/realtime.spec.ts`.
- **Bug real encontrado e corrigido nesta fatia — o WebSocket mockado nunca conectava de verdade.** Dois problemas independentes, ambos silenciosos (sem warning no console):
  1. `src/mocks/socket/socket-handlers.ts` usava `ws.link('*/socket.io/*')`. O binding nativo de WebSocket do MSW **remove o prefixo `/socket.io/` da URL do cliente antes de casar o padrão** (é como ele dá suporte "de fábrica" a Socket.IO — o padrão deve descrever o path *sem* esse prefixo). Como nosso padrão ainda continha `/socket.io/` literalmente, nunca batia; o handler de `connection` nunca era chamado e, com `onUnhandledRequest: 'bypass'`, o MSW fazia *passthrough* para uma conexão real — que falhava contra o `vite preview` (que não entende upgrade de WebSocket) sem nenhum aviso. Corrigido trocando para `ws.link('/')` (o path já sem o prefixo).
  2. Mesmo com o padrão corrigido, a conexão ainda falhava: `main.tsx` importava `@/app/router` estaticamente no topo do arquivo. Como imports estáticos são resolvidos antes do corpo do módulo importador rodar, isso carregava toda a árvore de rotas — e, transitivamente, `socket.io-client` — **antes** do `await enableMocking()` aplicar o patch em `globalThis.WebSocket`. `engine.io-client/transports/websocket.js` lê `globalThis.WebSocket` para uma constante de módulo (`const WebSocketCtor = globalThis.WebSocket || ...`) na primeira vez que é avaliado — se isso acontece antes do patch, a referência fica congelada na `WebSocket` nativa para sempre, e todo o mock de socket é ignorado silenciosamente pelo resto da sessão. Corrigido adiando `import('@tanstack/react-router')`, `import('@/app/router')` e `import('@/app/providers/app-providers')` para dentro de `bootstrap()`, depois do `await enableMocking()`.
  - Nenhum dos dois sintomas gerava exceção nem warning — só um erro de rede real e "silencioso" no console (`Error during WebSocket handshake: Unexpected response code: 200`), fácil de confundir com ruído do ambiente. Só foi descoberto ao tentar exercitar o cenário de preço/disponibilidade ao vivo do enunciado via Playwright; ambos os testes de tempo real (`e2e/cart.spec.ts`) ficam como regressão permanente para isso nunca voltar a quebrar silenciosamente.
- `src/mocks/dev-tools.ts` expõe `window.__mocks__.simulateNftUpdate(nftId, { priceEth?, available? })`: atualiza a edição no "banco" mockado (então um refetch REST nunca contradiz o evento) e propaga via `broadcastNftUpdated` — usado pelos testes de tempo real e também disponível no DevTools para demonstração manual.

## Mocks (MSW)

- `src/mocks/db.ts`: modelos `@mswjs/data` para todas as entidades do domínio (usuário, NFT, edição, favorito, item de carrinho, cupom aplicado por carrinho, cupom, pedido, carteira) — mesmo que nem todas tenham handlers REST ainda, o esquema já existe para as próximas features não precisarem remodelar o banco.
- `src/mocks/handlers/nft-mapper.ts`: converte um par `(nft, edition)` do banco no `NftSummary` da API (`toNftSummary`) e deriva o ID de token exibido a partir do id do NFT (`tokenNumberFor`) — usado pelos handlers de listagem, detalhe **e** carrinho, para nenhuma das três rotas divergir na forma/numeração do objeto.
- `src/mocks/seed.ts`: seed determinística (239 NFTs em 9 categorias, contagens batendo com o Figma; 2 usuários; 2 cupons — `LAUNCH10` válido e `EXPIRED5` já expirado, para exercitar os dois caminhos de erro do carrinho) com persistência em `localStorage`; `resetScenario()` limpa e reseeda. Versionada (`SEED_VERSION`): mudar a seed (ou o schema do banco, como a nova tabela `cartCoupon`) invalida automaticamente qualquer cenário salvo em um navegador antigo, em vez de deixar dados desatualizados/incompatíveis presos no `localStorage` de quem já tinha aberto o app antes.
- `src/mocks/scenarios/index.ts`: cenário ativo (`default` | `empty` | `latency` | `error`) lido pelos handlers a partir do `localStorage` — documentado no README.
- `src/mocks/socket/socket-handlers.ts`: usa `@mswjs/socket.io-binding` sobre `ws.link('/')` — ver a nota detalhada em "Tempo real (Socket.IO)" sobre por que o padrão precisa **excluir** o prefixo `/socket.io/`. Guarda os clientes conectados para permitir broadcast de `nft.updated` a partir de qualquer handler/cenário (`broadcastNftUpdated`, usado por `mocks/dev-tools.ts`). **Limitação**: o binding não implementa rooms/namespaces do Socket.IO — irrelevante aqui pois cada usuário só recebe eventos dos seus próprios recursos ativos, filtrados no cliente.
- Autenticação mockada (`src/mocks/auth.ts`) usa um esquema provisório de token (`token-<userId>`) emitido no login/cadastro; senhas são guardadas com hash (SHA-256 + sal fixo via `crypto.subtle`, síncrono o bastante para um mock — nunca em claro). O mesmo módulo resolve o "dono" do carrinho (`getCartOwnerId`): o `userId` do token quando autenticado, senão o header `X-Guest-Id` (ver seção Carrinho).

## Autenticação

- `src/features/auth/`: `model` (schemas Zod de login/cadastro + tipos de resposta), `api` (chamadas Axios), `viewmodel` (`useLoginForm`/`useSignupForm` com React Hook Form + Zod, `useLogout`), `ui` (`AuthModal`, `LoginForm`, `SignupForm`), `stores` (`authModalStore`, um Zustand só de UI — aberto/fechado + modo — separado do `sessionStore` em `shared/stores`, que guarda a identidade).
- O modal é montado uma única vez em `src/routes/__root.tsx` e controlado globalmente pelo `authModalStore`; o header só chama `authModalStore.getState().open('login')` — qualquer lugar do app pode abrir o modal sem precisar renderizá-lo localmente.
- Erros do mock: 422 (campos inválidos, tratado majoritariamente no client via Zod antes de bater na API), 409 no cadastro (e-mail já cadastrado, mapeado para o campo `email` via `form.setError`), 401 no login (credenciais inválidas, mensagem genérica de propósito — não revela se o e-mail existe).
- **Cuidado com o interceptor 401**: `shared/lib/http.ts` expira a sessão global (`sessionStore.getState().expire()`) em qualquer 401 — exceto nas próprias tentativas de `/auth/login` e `/auth/register` (que usam 401/409 para "essa tentativa falhou", não "sua sessão caducou") **e** exceto quando não havia sessão pra começo de conversa (`sessionStore.getState().user` precisa já existir) — um 401 anônimo (ex.: favoritar deslogado) só significa "isso exige login", não "sua sessão morreu". Sem a primeira exclusão, uma senha errada digitada por um usuário já logado derrubaria a sessão dele por engano; sem a segunda, o modal de "sua sessão expirou" (ver abaixo) abriria indevidamente pra quem nunca logou.
- Login/cadastro bem-sucedidos: `sessionStore.authenticate()` grava token+usuário (persistido via `zustand/persist`), invalida `['catalog']` (favoritos dependem de quem está logado) e fecha o modal — não há redirect, então "retornar ao fluxo anterior" (seção 3 do enunciado) é automático, já que a modal só sobrepõe a página atual.
- Logout (`useLogout`): chama `/auth/logout` (best-effort), limpa `sessionStore`, roda `resetSocket()` e invalida `['catalog']` — mesma lógica de "trocar de usuário", já que um novo login é só outro `authenticate()` por cima.
- **Bug real encontrado e corrigido ao testar navegação por teclado: o foco não voltava pro botão que abriu o modal.** Fechar o modal (Escape, clique fora, X) deixava o foco em `<body>` em vez de devolvê-lo pro trigger — o comportamento automático do Radix Dialog de restaurar foco depende de rastrear qual elemento abriu o diálogo, e como o `AuthModal` é aberto por botões soltos pelo app via `authModalStore.getState().open()` (Zustand), não por um `<Dialog.Trigger>` do próprio Radix, não havia nada pro Radix restaurar. Corrigido rastreando manualmente: `authModalStore.open()` guarda `document.activeElement` em `triggerElement` no momento de abrir; `AuthModal` usa `onCloseAutoFocus` (com `event.preventDefault()` pra suprimir o comportamento padrão do Radix e evitar corrida entre os dois) pra focar esse elemento explicitamente ao fechar. Testado em `e2e/accessibility.spec.ts`.

## Detalhe do NFT

- `src/features/nft-detail/`: mesma separação model/api/viewmodel/ui. `NftDetail` estende o `NftSummary` do catálogo (mesma imagem/preço/disponibilidade que o card mostrou, sem re-buscar o que já se sabia) com galeria, atributos, coleção, rede/contrato/royalty e avaliações.
- Rota `src/routes/nfts.$nftId.tsx`: o componente da rota renderiza `<NftDetailPage key={nftId} .../>` — trocar de NFT (ex.: pelo "Mais desta coleção") muda a `key`, o React remonta a subárvore e o estado local (imagem selecionada, quantidade, aba ativa) reseta de graça, sem precisar de um `useEffect` só para isso.
- **Galeria**: como só temos 4 artes fornecidas (não 4 fotos por NFT), a miniatura principal é sempre a mesma imagem do card que o usuário clicou — consistência entre catálogo e detalhe — e as outras 3 miniaturas ciclam pelas artes restantes como "ângulos" ilustrativos. Zoom abre a imagem ampliada num Dialog.
- **Quantidade e estoque**: a quantidade é clampada em `[1, available]` no próprio handler `+`/`-` (nunca só no submit) e o botão "Comprar" vira "Esgotado" e desabilita quando `available === 0` — cobre os requisitos de "limite de quantidade" e "edição indisponível" da seção 3 do enunciado sem precisar de uma tela de erro separada.
- **Atributos, avaliações e ID do token** são derivados deterministicamente do id do NFT no handler de mock (mesmo princípio dos preços/disponibilidade do catálogo: dado simulado, não aleatório) — nunca fica em branco, nunca muda entre reloads.
- **Compartilhar** é funcional de verdade: LinkedIn/Twitter abrem a URL de share-intent oficial de cada rede numa nova aba; e-mail usa `mailto:`. Nenhuma chave de API é necessária para isso.
- **"Mais desta coleção"** reaproveita `catalogQueries.list({ category })` (a mesma query do catálogo) filtrando o próprio NFT fora da lista — nenhum endpoint novo só para "relacionados". Os cards são o mesmíssimo `NftCard` do catálogo, só que numa linha com `overflow-x-auto` em vez de grid.
- **404 tratado de verdade**: acessar `/nfts/<id-inexistente>` direto (sem passar pelo catálogo) retorna 404 do mock e renderiza um estado "NFT não encontrado" com link de volta — não um crash nem uma tela em branco (seção 4 do enunciado: "tratamento de rotas inexistentes e acesso direto a qualquer tela prevista").

## Carrinho

- `src/features/cart/`: mesma separação model/api/viewmodel/ui das demais features. `CartQuote` (itens + subtotal/desconto/taxa/total) é sempre recalculada e devolvida inteira pelo mock a cada mutation (`POST/PATCH/DELETE /api/cart/...`) — o cliente nunca faz a conta "no escuro", a API é sempre a referência final (exigência explícita do enunciado: "a cotação da API é a referência para finalizar o pedido").
- **Carrinho de visitante sem login**: como favoritos/checkout exigem sessão mas carrinho explicitamente não (seção 3 do enunciado lista carrinho fora da lista do que exige autenticação), o "dono" do carrinho é resolvido por `getCartOwnerId` — `userId` do token se autenticado, senão um id de visitante gerado uma vez e persistido em `localStorage` (`shared/lib/guest-id.ts`), enviado em todo request via header `X-Guest-Id` (`shared/lib/http.ts`). Isso permite montar carrinho antes de logar.
- **Migração do carrinho ao autenticar**: `mocks/handlers/cart-handlers.ts#mergeGuestCart` roda dentro dos próprios handlers de `/auth/login` e `/auth/register`, lendo o `X-Guest-Id` do request de login — move (e soma quantidades, respeitando o estoque) os itens e o cupom aplicado do carrinho de visitante para o carrinho do usuário autenticado. Cobre literalmente "preservar os itens do visitante ao autenticar" sem nenhum passo extra do lado do cliente.
- **Cupom**: `POST /api/cart/coupon` normaliza o código (trim + uppercase), retorna 404 para código inexistente e 410 para expirado (`coupon.expiresAt` no passado) — dois status diferentes para as duas mensagens de erro pedidas ("código inválido ou expirado"). O cupom aplicado fica em `cartCoupon` (uma linha por dono de carrinho); se o cupom expirar depois de já aplicado, a próxima leitura do carrinho simplesmente para de aplicar o desconto (a linha em `cartCoupon` não é apagada automaticamente, então reaplicar o mesmo código depois de renovado funcionaria de novo — comportamento não exercitado nos testes).
- **Estoque ao vivo dentro do carrinho**: se a disponibilidade cai abaixo da quantidade guardada (seja por outra aba, seja pelo `nft.updated` simulado), o próprio `GET /api/cart` corrige a quantidade da linha para o novo teto e persiste — nunca deixa o carrinho "pedir" mais do que existe. Se a disponibilidade cai a zero, a linha continua visível (não some) com `isSoldOut: true` e `lineTotalEth: '0'`, para o usuário decidir remover ou esperar reposição, em vez de ver o item desaparecer sem explicação.
- **Taxa de rede**: `CART_NETWORK_FEE_ETH` (`features/cart/model/cart.ts`) é uma constante simulada fixa (`0.016`, cobrada só quando há ao menos um item não esgotado) — o enunciado deixa claro que é uma simulação ("taxa estimada"), então não há gás real nem RPC a consultar.
- **Recompute compartilhado cliente/servidor**: `features/cart/lib/cart-quote.ts#recomputeQuote` (subtotal → desconto → taxa → total, tudo com `decimal.js`) é a mesma função usada pelo handler de mock **e** pelas atualizações otimistas do `useCartViewModel` — evita que client e "servidor" cheguem a totais diferentes por terem duas implementações da mesma fórmula.
- **"Comprar" no detalhe do NFT** (`features/nft-detail/viewmodel/use-nft-detail-view-model.ts#buy`) agora chama `useAddToCart` de verdade em vez do placeholder — sucesso mostra um toast com ação "Ver carrinho" (`navigate({ to: '/cart' })`), erro (ex.: edição esgotada) mostra a mensagem da API. O contador do carrinho no header (`useCartItemCount`, em `SiteHeader`) lê a mesma query `['cart']`, então o badge atualiza sozinho sem nenhum evento manual.
- **"Colecionadores também viram"**: o componente `RelatedNfts` foi promovido de `features/nft-detail/ui/` para `shared/ui/` (com um prop `title`) para ser reaproveitado aqui exatamente como no detalhe — mesma UI, fonte de dados diferente (`catalogQueries.list({ sort: 'relevance' })` sem filtro de categoria, excluindo o que já está no carrinho).

## Perfil e carteiras

- **Rota protegida compartilhada**: `src/routes/_account.tsx` é uma layout route "pathless" do TanStack Router (prefixo `_`, sem segmento próprio na URL) que renderiza `AccountSidebar` + `<Outlet/>` e faz a checagem de sessão uma única vez em `beforeLoad` — `/profile` e `/wallets` (`_account.profile.tsx`, `_account.wallets.tsx`) herdam o guard automaticamente. Sem sessão: abre o modal de login (`authModalStore.getState().open('login')`) e redireciona para `/` (`throw redirect({ to: '/' })`) antes de qualquer render — cobre "perfil, carteiras... exigem autenticação" (seção 3) sem duplicar a checagem em cada rota.
- **`AccountSidebar`** (`app/layout/account-sidebar.tsx`) reflete o menu do Figma por completo — "Dados do perfil" e "Carteiras" navegam de verdade; "Atividade", "Lista de interesse", "Ofertas", "Arquivos baixados" e "Suporte" ficam como toast "chega em breve" (fora do escopo da entrega, conforme a seção 3 do enunciado exclui essas páginas explicitamente); "Sair" chama o mesmo `useLogout` do header.
- **Modelo de usuário estendido**: `AuthUser`/`SessionUser` ganharam `username` e `ensName` (antes só `id/name/email/avatarUrl`). No cadastro, o username é gerado automaticamente a partir do nome (`mocks/auth.ts#generateUniqueUsername` — normaliza acentos, remove símbolos, desambigua com sufixo numérico) para não adicionar campo nenhum ao modal de cadastro; o colecionador só o vê/edita depois, no Perfil.
- **Sincronização sessão ↔ perfil**: `sessionStore` ganhou `updateUser()` — ao salvar o perfil com sucesso, o header (avatar, nome) atualiza na hora, sem precisar de refetch de sessão nem re-login.
- **Avatar**: upload real via `FileReader` → data URL (sem backend de arquivos: o mock guarda a string no próprio registro do usuário), com limite de 2MB verificado no cliente antes de ler o arquivo. "Remover" volta para o placeholder determinístico (`placeholderImage(userId)`) — o mesmo gerador usado no seed, não uma imagem em branco.
- **Alterar senha é opcional dentro do mesmo formulário**: os três campos (`currentPassword`/`newPassword`/`confirmNewPassword`) só são validados (via `superRefine` em `features/profile/model/profile.ts`) se pelo menos um deles for preenchido — salvar só nome/e-mail/ENS nunca exige senha. O mock revalida a senha atual server-side (`verifyPassword`) antes de trocar o hash; nunca confia só na validação client-side.
- **Conflito de username/e-mail**: `PATCH /api/profile` responde 409 (com `fieldErrors`) quando o novo username ou e-mail já pertence a outro usuário — o mesmo padrão de erro usado no cadastro (seção Autenticação), reaproveitado pelo `form.setError` do React Hook Form.
- **Carteiras — divergência deliberada do Figma**: no frame de Carteiras, os campos "Nome de exibição", "Nome do perfil", "E-mail" e "Código de indicação" são idênticos aos do Perfil/duplicados sem função própria de carteira (um endereço de carteira não tem e-mail). Implementei o formulário só com os campos que descrevem a carteira em si — apelido, rede, endereço, tipo (MetaMask/WalletConnect/Coinbase) e ENS opcional — e removi os campos de identidade do colecionador, que já vivem no Perfil. Decisão confirmada com o usuário antes de implementar (ver também a mesma divergência prevista para o formulário de Pagamento).
- **Carteira principal e secundária**: `db.wallet` guarda no máximo uma linha `isPrimary: true` e uma `isPrimary: false` por usuário; `PUT /api/wallets/:slot` faz upsert (cria se não existir, atualiza se existir) e `DELETE /api/wallets/secondary` remove — a principal não pode ser removida pela API (409), só editada, já que o pagamento sempre precisa de ao menos uma carteira. O botão "Usar os mesmos dados da carteira principal" (`copyPrimaryIntoSecondary`) só copia os valores para o formulário da secundária — nada é salvo até o colecionador confirmar com "Salvar carteira secundária".

## Pagamento e confirmação de pedido

- `src/features/checkout/` (tela `/checkout`, protegida por `requireAuth`) e `src/features/orders/` (tela `/orders/$orderId`, o recibo/confirmação) — duas features separadas porque o enunciado as lista como duas telas distintas na seção 3, mesmo a confirmação do Figma sendo desenhada como um modal: implementei como rota própria (não um `<Dialog>`) para o recibo ter URL real, sobreviver a refresh e não desaparecer se o usuário reabrir a aba — o card é só estilizado para parecer o modal do Figma (`border border-primary`, `rounded-2xl`, botão "X" que navega para `/`).
- **Formulário de pagamento — mesma divergência do Figma já resolvida em Carteiras**: o frame duplicava os campos do formulário de carteira (rede, endereço, tipo, código de indicação...) dentro de "Perfil do colecionador" no checkout. Meti só o que faz sentido revisar/confirmar num checkout: nome de exibição, e-mail, ENS e uma observação opcional — pré-preenchido a partir do `/api/profile` (mesma query `['profile']` da tela de Perfil, sem endpoint novo) e editável ali mesmo, sem navegar para outro lugar. A seleção de carteira/rede vive só no painel direito, lendo as carteiras já cadastradas (`/api/wallets`) — nunca duplicando o cadastro.
- **Simulação de conexão, recusa e desconexão** (`features/checkout/viewmodel/use-checkout-view-model.ts#connectWallet`): selecionar uma carteira dispara um estado `connecting` (~700ms, imita a latência de um popup de extensão) e então decide **recusar de verdade** se a rede da carteira não for Ethereum — todas as coleções desta loja são "Ethereum" (`nft-detail`), então uma carteira Polygon/Solana cadastrada é um motivo real de recusa, não um erro aleatório. Isso cobre as quatro exigências da seção 4 do enunciado ("seleção de rede e simulação de conexão, recusa e desconexão") com uma única peça de lógica significativa em vez de simular recusa com `Math.random()`. "Desconectar" só zera o estado local (`idle`) — reconectar exige selecionar de novo.
- **Revalidação da cotação antes de confirmar**: `POST /api/orders` recebe `expectedTotals` (o que o cliente está vendo) e recalcula a cotação atual via `buildQuote` (a mesma função do carrinho) — se subtotal/desconto/taxa/total não baterem exatamente, responde 409 sem criar o pedido. O cliente reage invalidando `['cart']` (os números na tela atualizam sozinhos) e exige um novo clique deliberado em "Confirmar compra" — não há retry automático, então a reconfirmação é sempre um ato consciente do usuário, como pede a seção 4 ("mudanças devem exigir nova confirmação").
- **Idempotência real** via `shared/hooks/use-idempotency-key.ts` (já existia no scaffold, nunca tinha sido consumido): a chave é gerada uma vez e persistida em `sessionStorage`, então sobrevive a um refresh no meio do fluxo — reenviar a mesma chave depois de um timeout/reload devolve o pedido já criado (`db.order` é buscado por `{userId, idempotencyKey}` antes de criar um novo) em vez de duplicar a compra ou descontar o estoque duas vezes. A chave só é renovada (`renew()`) quando o servidor rejeita por 409 — cotação desatualizada ou chave reaproveitada com conteúdo diferente são, nos dois casos, intencionalmente um pedido *diferente*, não um reenvio do mesmo.
- **Reaproveitar a chave com conteúdo diferente é conflito, não um "devolve o que já existe" genérico** (`mocks/handlers/orders-handlers.ts#buildRequestFingerprint`): junto do pedido, o mock guarda um fingerprint (`JSON.stringify` normalizado de `walletSlot` + dados do colecionador + `expectedTotals`) tirado do corpo da requisição original. Um reenvio com a mesma `idempotencyKey` só é tratado como a mesma tentativa (devolve o pedido existente) se o fingerprint bater; se bater a chave mas não o conteúdo, responde 409 em vez de devolver silenciosamente um pedido que não corresponde ao que foi pedido agora — exigência explícita da seção 5 do enunciado ("reutilizar a chave com conteúdo diferente deve gerar conflito").
- **Pendente / confirmado / recusado, de forma assíncrona de verdade**: `POST /api/orders` cria o pedido com `status: 'pending'` e responde imediatamente com `201`; a resolução (`confirmed` ou `declined`, decidido pelo cenário `declined` — ver README) acontece ~1.5s depois. Como o mock roda inteiramente no browser (sem processo de servidor real), um `setTimeout` sozinho não sobreviveria a um reload no meio do processamento — por isso a resolução é "preguiçosa": `resolveOrder()` (`mocks/handlers/orders-handlers.ts`) roda tanto no `setTimeout` quanto em toda leitura (`GET /api/orders/:id`), comparando `Date.now()` com `processingCompletesAt` guardado no registro. Isso torna o sistema correto independente de a aba ter ficado aberta ou não: um reload durante o processamento não duplica nada, só recalcula se já passou tempo suficiente. `/orders/$orderId` renderiza um card diferente por status (`OrderPendingCard` novo, com spinner); a tela de "Obrigado" (`OrderConfirmedCard`) só aparece quando `status === 'confirmed'` (seção 4: "exibir a confirmação somente para pedido efetivamente confirmado").
- **`order.updated` via Socket.IO**: ao resolver (`resolveOrder`), o mock emite `order.updated` (`{id, resource: 'order', version, data: {orderId, status}}`) reaproveitando a mesma infraestrutura de broadcast do `nft.updated` (`broadcastOrderUpdated`, mesmo `activeClients`). `useOrderViewModel` assina o evento, filtra pelo `orderId` da tela atual e usa `createEventVersionTracker` (mesmo helper do catálogo) para tolerar entrega duplicada ou fora de ordem antes de invalidar `['order', orderId]`. Como salvaguarda redundante (caso o socket esteja desconectado), a query do pedido também usa `refetchInterval` condicional (`800ms` só enquanto `status === 'pending'`, `false` depois) — o socket resolve na hora; o polling é só um fallback.
- **Cenário de timeout na criação do pedido**: `localStorage.setItem('nft-marketplace.scenario', 'timeout')` faz o handler de `POST /api/orders` nunca responder (`await new Promise<never>(() => {})`). O client usa `timeout: 2500` no Axios especificamente nessa chamada (maior que o pior caso do cenário `latency`, ~1.6s, para não gerar falso positivo) — ao estourar, mostra "Não foi possível confirmar se o pedido foi recebido... não será cobrado em duplicidade" **sem renovar a idempotency key** (diferente do tratamento de 409, que sempre renova — aqui a intenção é deliberadamente *reenviar a mesma tentativa*). Reenviar depois que o cenário volta ao normal recupera o mesmo pedido via o fingerprint de idempotência (não compra em duplicidade, não desconta estoque duas vezes) — testado em `e2e/checkout.spec.ts`, incluindo a asserção de que só uma unidade foi descontada do estoque no total.
- **Preservar itens em falha, remover só o comprado**: se o pedido é recusado (ou a cotação está desatualizada, ou falta carteira), o mock nunca toca no carrinho nem no estoque. Só em caso de sucesso: decrementa `edition.available` de cada item comprado (e propaga isso via `broadcastNftUpdated`, então outra aba/usuário vê o estoque cair em tempo real — reaproveita a mesma infra de `nft.updated` do carrinho) e chama `clearCart` — como o checkout desta fatia sempre compra o carrinho inteiro de uma vez, "remover só os itens comprados" e "esvaziar o carrinho" coincidem.
- **Recibo é um snapshot congelado**: `OrderSnapshot` é serializado (`JSON.stringify`) dentro do registro do pedido no momento da confirmação — preços, quantidades e taxas ali nunca mudam depois, mesmo que o catálogo mude (testado explicitamente: um `nft.updated` simulado depois da compra não altera o preço mostrado no recibo). "ID da transação" e o link "Ver no Etherscan" são simulados (`crypto.getRandomValues` gerando um hash de aparência real) — nenhuma chamada de rede de verdade, como pede a seção 4.
- **Tempo real no checkout**: a mesma `useCartRealtimeSync` do carrinho (ver seção Carrinho) roda na tela de pagamento — se o preço/disponibilidade mudar enquanto o usuário está revisando o pedido, o resumo à direita atualiza e avisa por toast antes mesmo de tentar confirmar.
- **Expiração de sessão durante o checkout, com retomada do contexto**: `sessionStore.isExpired` já existia mas nada o consumia — um 401 marcava a sessão como expirada e não acontecia mais nada visível. Agora `shared/hooks/use-session-expiry-modal.ts` (montado uma vez em `__root.tsx`, igual à reconciliação de socket) reage a essa flag abrindo o modal de login **por cima** da tela atual, sem navegar nem desmontar nada — é essa ausência de navegação que preserva o contexto: o formulário do colecionador (React Hook Form em `useCheckoutViewModel`, nunca desmontado) e o estado local de conexão da carteira continuam exatamente como estavam. Ao logar de novo, `sessionStore.authenticate()` zera `isExpired`, o modal fecha sozinho (mesmo fluxo de `useLoginForm`) e o usuário só precisa clicar em "Confirmar compra" de novo — sem re-preencher nada. Simulação disponível via `window.__mocks__.expireSession(userId)` (revoga o token corrente no "banco" mockado até o próximo login bem-sucedido) e o handler de `POST /api/orders` passa a tratar `kind: 'unauthorized'` com uma mensagem própria ("Sua sessão expirou... os dados preenchidos aqui serão mantidos") em vez do erro genérico. Testado em `e2e/checkout.spec.ts`.
  - **Cuidado descoberto ao implementar isso**: reagir a *qualquer* 401 global (via o interceptor de `shared/lib/http.ts`) quebrou o teste de favoritar sem login — favoritar deslogado sempre respondeu 401 e sempre reverteu silenciosamente o optimistic update (comportamento documentado, intencional), mas o modal de sessão-expirada passou a abrir por cima também nesse caso, mesmo nunca tendo existido uma sessão para expirar. Corrigido no próprio interceptor: só marca `isExpired` quando `sessionStore.getState().user` já existia no momento do 401 — um 401 anônimo é só "isso exige login", não "sua sessão morreu".

## Testes E2E

- **Três viewports**: `playwright.config.ts` define `chromium-desktop` (1440×900), `chromium-mobile` (Pixel 7) e `chromium-tablet` (768×1024). O tablet roda só `e2e/responsive-tablet.spec.ts` (via `testMatch`) — não faz sentido triplicar a suite inteira só pra cobrir mais um breakpoint; em vez disso, esse arquivo assinala especificamente o que muda *só* em tablet: a nav secundária do header aparece (breakpoint `md`, ausente em 390px) enquanto a sidebar do catálogo ainda empilha em vez de ficar ao lado do grid (abaixo do breakpoint `lg`, diferente de 1440px) — um estado intermediário real, não coberto por nenhum dos outros dois viewports.
  - **Bug de config encontrado**: `testMatch` só restringe o que o projeto tablet roda — não exclui o arquivo dos outros projetos. Sem `testIgnore` correspondente em `chromium-desktop`/`chromium-mobile`, a suite tablet rodava (e falhava) nos três projetos, já que as asserções são especificas de 768px.
- **Regressão visual** (`e2e/visual.spec.ts`, baselines em `e2e/visual.spec.ts-snapshots/`, versionadas): escopo deliberadamente pequeno — só telas estáticas/determinísticas (grade do catálogo, carrinho vazio, detalhe do NFT), nunca a página inteira (mais frágil entre ambientes/fontes), sempre com `animations: 'disabled'` e uma tolerância pequena (`maxDiffPixelRatio: 0.02`) pra não quebrar por antialiasing. Atualizar depois de uma mudança visual intencional: `bunx playwright test e2e/visual.spec.ts --update-snapshots`.
- **Navegação por teclado e foco de diálogos** (`e2e/accessibility.spec.ts`): abrir o modal só por `focus()` + Enter (não `.click()`, pra provar que o disparo funciona por teclado de verdade); focus trap verificado fazendo Tab por mais paradas do que existem elementos focáveis no diálogo (se algum dia escapar, a asserção `dialog.locator(':focus')).toHaveCount(1)` falha na hora) — sem hardcodar qual elemento é focado em cada parada, já que a ordem de tab exata é um detalhe de implementação frágil de mais pra fixar num teste. Achou e ajudou a corrigir o bug de foco-não-retorna documentado em "Autenticação" acima.
- **Eventos de socket "crus"**: `mocks/dev-tools.ts#broadcastRawNftUpdate` emite exatamente o evento dado (sem tocar no "banco" mockado), diferente de `simulateNftUpdate` — deixa os testes escolherem a versão de propósito pra provar que o `createEventVersionTracker` do client rejeita duplicatas e eventos antigos de verdade (não só "parece que funciona"), coisa que não dá pra testar de outro jeito já que o mock normal sempre incrementa a versão automaticamente.

## Desvios e limitações

- **Filtro por rede**: exibido com contagens reais do Figma, mas ainda não filtra (nosso modelo de NFT não tem campo de rede); vira funcional se/quando isso for modelado.
- **Auditoria Lighthouse** (seção 10 do enunciado): `scripts/lighthouse-audit.mjs` — não usei `@lhci/cli` (permanece instalado, mas o formato de saída dele não cobre bem o que a seção 10 pede: mediana de 3 execuções por categoria, LCP/CLS/TBT explícitos, relatório com ambiente/condições). O script usa a API Node do `lighthouse` diretamente: builda (`bun run build`), sobe `vite preview` local, roda 3 medições de Início (`/`) e Detalhe do NFT (`/nfts/nft-3`) em mobile (config padrão do Lighthouse) e desktop (`lighthouse/core/config/desktop-config.js`), salva HTML+JSON de cada run em `lighthouse/reports/<página>-<perfil>/run-N.{json,html}` e gera `lighthouse/REPORT.md` com a mediana por categoria, métricas individuais, ambiente de execução (versões, SO, CPU, **carga do sistema no momento da run** — é uma máquina de desenvolvimento compartilhada, não um runner isolado, o que é registrado explicitamente porque Performance é sensível a isso) e uma seção de causas para qualquer categoria abaixo da meta. Comando: `bun run lighthouse`.
  - **Resultado real**: Accessibility (95–100), Best Practices (100) e SEO (100) batem a meta em todas as combinações. Performance fica abaixo da meta (64–95, variando com a carga da máquina) — causa identificada e documentada no próprio `REPORT.md`: o build de produção inclui a camada de mocks inteira (MSW + `@mswjs/data`, chunk de ~920 KB) porque não há backend real, o que empurra LCP/TBT para cima especialmente no perfil mobile. Deliberadamente não desativei os mocks para inflar a nota — a seção 10 do enunciado exige que a auditoria carregue as funcionalidades reais da entrega.
  - **Bug real encontrado e corrigido durante a auditoria**: CLS de 0.224–0.306 no Detalhe do NFT desktop. Investigando com o audit `layout-shifts`/`cls-culprits-insight`, a causa raiz é a troca de fonte (`font-display: swap` da fonte variável Roboto Mono via `@fontsource-variable/roboto-mono` — o texto pinta primeiro com a fonte de fallback e reflui quando a fonte monoespaçada carrega, empurrando o footer). No caminho, também encontrei e corrigi um bug secundário real (não a causa raiz do CLS, mas um mismatch genuíno): `RelatedNfts` (`shared/ui/related-nfts.tsx`) usava `CatalogSkeleton` — um grid de várias linhas — como placeholder de loading para o que na verdade renderiza como uma única linha horizontal de cards de 219px; a altura do skeleton não batia com o conteúdo real, causando um segundo salto de layout ao trocar. Corrigido com um skeleton dedicado que espelha a estrutura exata do `NftCard` (mesmas classes/espaçamento) e reserva o espaço da fileira de bolinhas de paginação também. A troca de fonte continua não corrigida (não há como sobrescrever `font-display` de um só `@font-face` do pacote sem reimplementar todos eles; a correção correta é pré-carregar o `.woff2` específico ou usar `font-display: optional`) — registrada como causa no `REPORT.md`, não escondida.
  - `index.html` ganhou `lang="pt-BR"` (estava `en`, incorreto para o conteúdo) e uma meta description (faltava, derrubava SEO); `public/robots.txt` criado (sem ele, `vite preview`/SPA fallback devolvia o `index.html` no lugar, e o audit `robots-txt` reprovava por sintaxe inválida) — ambas correções legítimas descobertas pela própria auditoria, não gaming de pontuação.
- **OAuth (Google/Facebook) e "esqueceu a senha"**: os botões existem com o visual completo, mas são placeholders (`notImplementedToast`) — implementar OAuth de verdade exigiria um provedor real, fora do escopo de um mock.
- **Favoritar sem sessão**: hoje só reverte o estado otimista silenciosamente quando a API responde 401 (sem mensagem explicando "faça login para favoritar") — o mesmo comportamento já existia no catálogo antes desta fatia; ficou por cobrir/melhorar quando o fluxo de auth-gating for revisitado.
- **Cupom expirado após aplicado**: se um cupom já aplicado expira enquanto o carrinho está aberto, o desconto some silenciosamente na próxima leitura (sem toast avisando "seu cupom expirou") — o carrinho não assina nenhum evento de expiração de cupom, só de `nft.updated`. O checkout ainda revalida o cupom indiretamente (faz parte da cotação comparada em `POST /api/orders`), então um cupom que expirou entre o carrinho e o pagamento *é* pego — só não gera um aviso específico de "cupom expirou", cai no aviso genérico de "os valores mudaram".
- **Endereço de carteira validado de forma genérica**: como o formulário de Carteiras aceita Ethereum, Polygon e Solana (formatos de endereço bem diferentes — hex `0x...` vs. base58), a validação é só "6 a 64 caracteres", sem regex por rede. Suficiente para o mock (nunca há uma blockchain real do outro lado), mas não pega um endereço com formato claramente errado para a rede escolhida.
- **Avatar sem redimensionamento**: o upload lê o arquivo como data URL sem passar por um canvas para redimensionar/comprimir — só um limite de 2MB no cliente. Para o mock (armazenado em `localStorage`) é suficiente; um app real faria resize antes de persistir.
- **Checkout compra o carrinho inteiro de uma vez**: não há seleção parcial de itens na tela de pagamento (o Figma também não mostra isso) — "revisão antes do envio" é só dos dados do colecionador e da carteira, não das quantidades (isso já foi revisado no carrinho, com o link "Tem um código promocional? Aplique aqui" levando de volta para lá se precisar mudar algo).
- **Bug real encontrado e corrigido ao implementar `order.updated`/reconciliação — regressão universal no mock de WebSocket.** Expor `disconnectSocket`/`reconnectSocket`/`simulateSocketReconnect` em `window.__mocks__` (para os testes de `e2e/realtime.spec.ts` conseguirem simular desconexão) levou `src/mocks/dev-tools.ts` a importar `getSocket` estaticamente no topo do arquivo. Como `src/mocks/browser.ts` importa essas funções de `dev-tools.ts`, e `browser.ts` é o primeiro módulo carregado dinamicamente em `main.tsx#bootstrap()` — **antes** de `await enableMocking()` rodar —, isso recriou exatamente o bug já documentado acima em "Tempo real (Socket.IO)": `engine.io-client` capturava `globalThis.WebSocket` (ainda o nativo) numa constante de módulo antes do patch do MSW acontecer, e todo socket subsequente na sessão falhava silenciosamente (`Error during WebSocket handshake: Unexpected response code: 200`), em qualquer página, sempre — não uma falha específica de uma rota. Corrigido tornando o acesso ao socket dinâmico dentro de `dev-tools.ts` (`await import('@/shared/lib/socket')` dentro de cada função exposta, resolvido só quando de fato invocada, quando o bootstrap já terminou). Reforça a lição já registrada acima: qualquer novo import (direto ou transitivo) de `socket.io-client` a partir de um módulo alcançável antes de `enableMocking()` reintroduz esse bug — vale conferir a árvore de imports sempre que se mexe em `mocks/browser.ts` ou nos módulos que ele importa.
- **Segundo bug encontrado no mesmo trabalho: badge do carrinho ficava com contagem desatualizada.** `useCheckoutViewModel` invalidava `['cart']` no `onSuccess` da criação do pedido — mas nesse momento o pedido acabou de nascer `pending`, e o carrinho só é limpo no servidor quando ele *resolve* para `confirmed` (`resolveOrder`). O refetch disparado ali buscava um carrinho que ainda tinha os itens, e nada invalidava `['cart']` de novo quando a resolução de fato acontecia (nem via socket, nem via o polling de fallback) — o badge do header ficava preso mostrando a contagem antiga até uma navegação forçar um refetch. Corrigido em `useOrderViewModel`: um efeito rastreia o status anterior do pedido e invalida `['cart']` especificamente na transição `pending → (confirmed | declined)`, não na criação.
